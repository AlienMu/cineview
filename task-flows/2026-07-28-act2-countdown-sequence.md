## 整改（逐条，含为什么这样改）

### 1. 几何：`EXTENT` 由几何**解出**，不再猜

- 把 bar 四角**按绘制用的同一变换**绕 HINGE 旋转，与词带（含其环绕振幅）一起求凸包 → `EXTENT`。
  开角、铰点、词带位置将来任意改动，盒子自动跟着对，不会再退化。
- **两次自伤，都由实测抓回来**（这是本轮最该记住的部分）：
  1. 第一版只包了「板 + 词带矩形」，漏了**环绕振幅** → 复测底边缘亮像素
     **9(手机) / 19(1280) / 35(1440)** dev px：从裁杆变成裁词。→ 引入 `WORD_OVERSCAN`
     （`WORD_ORBIT_MAX + WORD_DOT_PAD`），并把轨道半径常量提到模块级，让绘制与 `EXTENT`
     **读同一个数**，无法再漂。
  2. 补完后上边缘仍有 **23/15/14** dev px：`EXTENT` 是**粒子中心**的凸包，而粒子是**方块**，
     半个方块画在凸包外；高度是约束维时凸包正好贴满盒子 → 引入 `BOARD_DOT_PAD = 0.009`。
- **复测（三档视口 × 两个关键帧）**：`form=1 & deg=34`（板全开、组装完成）与 `settled`（word=1）
  四边亮像素 **全部 0**。

### 2. 构图：缩放看开板包络，居中看**落位**画面

`EXTENT` 含开板上举杆的左摆（x=−0.083），但那只存在几百毫秒。用它居中 → 落位帧左侧永久空出
**50px 对右侧 11px**（78 dev px 偏差）。故拆成两件事：**缩放**用完整包络（保证永不裁切），
**位置**居中于「板体 + 词带」即长期在屏的画面，并加 clamp——若居中会把开板包络推出画布则退让。
另外把 0.96 内缩**同时施加于高度**（原先只有宽度）：高度是约束维时 clamp 毫无余量、`oy` 被
钉在上限，居中根本无法生效（实测上 296 / 下 7 dev px）。

- **复测**：水平偏差 78 → **8（手机）/ 20（笔记本）** dev px；直接量最终 PNG：左 **85** / 右 **92**，
  偏差 **7**。垂直 284/49 是**已知取舍**——高度为约束维时优先保住开板抬头空间，不为居中牺牲裁切。

### 3. 321 卡顿：`REFORM_START` 改为**等于**末拍终点

`REFORM_START = COUNT_BEATS[last].end`（由数据推导，不再手写常量），空窗归零。

- **复测**（帧间像素差分，按 progress 定位跳变）：**0.83 已从 top-10 尖峰列表中消失**；
  剩余最高尖峰在 **0.945–0.95**，那是**合板闪光**（设计如此，硬闪）。

### 4. 灯光：光池从词带移回板面

`radial-gradient(58% 14% at 50% 72%)` → `52% 16% at 50% 45%`。

- **复测**：板带 **48.06** vs 词带 **33.75**（改前 45.87 vs 49.18）→ 主次关系反转成正确方向。

### 5. ACTION：暗金 + 渐变 + 环绕

- 颜色走 `goldRamp()`（`GOLD_DEEP → GOLD → AMBER`，全程暗金，**不含暖白**），按粒子目标 **X**
  取样，使渐变沿字横向铺开而非随机噪点；叠一条缓慢行进的 shimmer 让渐变本身在动。
- 环绕：每颗粒子有自己的半径/相位/方向（相邻反向），振幅刻意很小（s≈350 时约 0.6–1.5px）——
  再大 dot-matrix 就糊成一团、`ACTION` 不再可读。
- **帧跳过守卫同步放宽**：原逻辑「progress 与 phase 未变就不重绘」会在拖拽停在 1.0 的**那一刻**
  冻结环绕，而那正是词完全成形、最该看到动的时候 → 增加 `timeDriven` 判断。
- **复测**：粒子平均色 **rgb(170,128,63)**（改前 236,227,208 暖白）、**275** 种不同颜色（渐变存在）；
  progress 锁定 1.0 时画布仍推进 **26** 次绘制、**1236** 个像素在变（环绕在跑）。

### 6. 持续动画：接框架泳道，不用 CSS 无限动画

`s02-clapper` 增加 `infiniteAnimation`（`scale [1,1.006,1]`、`y [0,−0.35%,0]`、9000ms、
`timing.reduced` 时为 `undefined`）。幅度刻意极小：三脚架上的板子是「随房间呼吸」，不是摆动；
再大就会和同一盒子内的画布粒子打架、把字拖花。
框架在 drag 模式下会**多插一层匿名 `motion.div`**（`Animate.tsx` 已确认），该层会收缩到高度 0
导致绝对定位画布塌陷——与灯组各层、act4 streams 同一类缺陷，已补 CSS 让其充满 holder。

### 7. 分界线/遮罩

实测证明没有 DOM 遮罩层可删（见根因表）。用户感知到的「薄雾盖住底色」来自灯组三层叠加，
本轮光池重定向已改变其分布；其余强边缘是画布上板子自己的线条，属应有之画，不动。

## 探针本身的三处修正（本轮同样重要）

1. `act2-word-probe.mjs` **硬抄了一份旧 `boxOf` 公式**（`s = min(w*0.96, h*0.78)`、`oy` 按 `s*1.24` 居中）。
   几何一改，它就在**错误的带**里取样，报出 `wordReadsAsSixLetters: false`——一个**并不存在的回归**。
   → 画布新增 `data-box-ox / box-oy / box-s` 发布**真实**盒子，探针改为**读**几何而不是重算。
   教训：复制一份公式的探针，会在公式变更时**静默停止测试它声称测试的东西**。
2. 同一探针的「六个字母」判据用**全局 gap 阈值**做聚类，这在原理上不可测：字内点间距 7–8px、
   窄字 `I` 两侧 16px、字间 25–26px，**没有任何单一常量能同时分开三者**（阈值 w*0.012 数出 10 簇、
   w*0.02 数出 7 簇，而两次画面都是对的）。→ 改为**结构判据**：对内部间隙排序、切最大的 N−1 处，
   再看 `separation`（第 N−1 大 / 第 N 大间隙）与 `evenness`（最窄/最宽字身）。
   阈值取自**实测分布**而非猜测：词 separation **1.41–2.0**、evenness **0.88–0.90**；
   对照带（板面数据行）separation **1.0**、evenness **0.01** → 判据有区分力（90× 差距）。
3. `act2-sequence-probe.mjs` 在**不传 `--span`** 时 `indexOf` 返回 −1、取到 `argv[0]`（node 路径）
   → `span = NaN` → `mouse.move` 抛 `Invalid parameters`，**整个探针崩溃**。
   我先前把「suite 输出里没有 FAILED 行」误读成通过——**缺少失败行不等于通过**。已修。

## 根因（读码 + 时序算术，动手前定位）

上一轮「入场动画全部没有 / 合板被改掉」是**同一个根因：整段序列在场景可见之前就跑完了**，
不是公式被改（`particleField.ts` 与 clap 公式本轮之前一行未动，可 diff 核对）。

算术：`TemporalDragExperience.tsx` 的 `dragTimeScale: 100` → 元素时钟 = 拖拽百分比 × 100ms
（`useElementTrack.ts` 的 `dragTimeScalePer100`，跟手段 `elapsed = r × 100 × dragTimeScale`）。
提交阈值 `minRatio 0.15` / `maxRatio 0.32` → 典型释放已消耗 **1500–3200ms** 的编排时间。
而 `s02-clapper` 的 enter 只有 **2100ms**：

- 释放瞬间 progress ≈ 1500/2100 = **0.71**，早已越过 `CLAP_START = 0.62` →
  **合板发生在手指还在屏幕外/场景尚未落位的那段时间**，用户看到的第一帧就是「板已合上」。
- 灯组 enter 620–760ms → 在 6%–8% 拖拽内就满亮，同理不可见。
- 释放后 `useElementTrack` 的 settle 只把**剩余** 600ms 按真实速率补完 → 几乎没有可看的尾巴。

结论：**enter 预算必须远大于典型释放消耗的 1500–3200ms**，让「可看的高潮段」落在释放之后的
settle 里（framework 会以真实速率播完剩余），同时前段仍然跟手。这是框架已有语义，不需要自造。

## 本轮判据（与上一轮不同：全部以「用户能看到」为口径）

1. **场景落位时 progress < 0.5**：释放（15%）后场景开始落位的那一刻，canvas `dataset.progress`
   必须仍在 FORM 段（< 0.5），否则一切「入场动画」都不可见。上一轮此值 ≈ 0.71 → 失败根因。
2. **合板发生在可见期**：`dataset.openDeg` 从 >30° 变到 ~0° 的整个过程必须发生在场景 opacity/位置
   已落位之后（时间戳比较）。
3. **倒计时三个数字都渲染过**：`dataset.count` 依次出现 `3`、`2`、`1`，且每个数字都有 ≥1 帧
   被真正绘制（数值列粒子已重组到 digit 目标）。
4. **ACTION 最后出场**：其有效 opacity 起点晚于 clap 结束时间，且有进场与退场（反向拖拽时降回）。
5. **零青色**：第二幕帧内不得出现 teal 像素（b > r 且 b > 90 的像素数为 0）。
6. **灯组入场可见 + 持续动效可察觉**：落位后灯层 opacity 仍在上升；settle 后光锥 transform 变化
   幅度 ≥ 1.0°（不是只有 0.01 的数值抖动）。

### 1. `act2-digit-legibility` 的两处坏指标（导致 3/2/1 长期误报不合格）

**坏指标 A：基线差分的前提已被我自己破坏。** 探针原本用「倒计时帧 − settle 帧」差分，
前提是家具（格线/边框/标签）两帧相同、相减即消，只剩数字。但本轮的遮蔽（occlusion）改动

判据全域触发。实测后果：数字只占裁切区不到一半，差分 bbox 却填满 96 格中的 94-96 格，
5x7 矩阵是噪声，三个数字全部落在 0.60-0.63（约等于瞎猜）。

| hold "3" | 250 | 716 | 2768 |
| hold "2" | 249 | 712 | 2550 |
| hold "1" | 278 | 674 | 2564 |
| settled | 593 | 1878 | — |

把 `settledMaxLit` 抬到 1586，于是「阈值是否只含数字」恒假。改为要求数字出现过之后才计。
修正后 `settledMaxLit=0`，即该阈值在 settle 帧上不含任何家具像素。

**坏指标 B：探针自带一份模板，并且已经漂移。** 这是本轮最值得记的一条。探针内联的 `3` 是
`11111/...1./..1../...1./....1/1...1/.111.`，而 `particleField.ts` 实际绘制的是

## 第七轮（act 4：入场无感知 / 数字无持续动画）

用户报告：`act4入场动画无感知，数字无持续动画`。两条都实测复现，且都不是"感觉"问题。

### 1. 入场无感知 —— 预算根因（与 act 2 同一个病）

元素时钟按 100ms/1% 推进，真实手势落位已消耗 3000ms+；而 act 4 的 enter 预算是
260-520ms（per-char 只有 150ms）。probe（`scripts/act4-enter-perception.mjs`）量的是
"落位之后还有多少个不同的 inline style"：修复前 6 个元素全是 **1**，即入场全部在屏幕外跑完。

### 2. 我自己制造的回归：串行链的累加预算

第一次修复只是把每个 enter 调长（slate 6000 / label 4600 / ring 5200 / equation 3400），
结果 `s04-equation` 卡在 `opacity: 0` —— 不是"提前跑完"，是**从未开始**。
链是 slate → label → 11 个 char → ring → equation，`waitFor` 串行累加后 equation 的起点
落在 ~16.8s 元素时钟，而在屏窗口只有 ~5.7s。

把 3400 改 6000 完全没有变化（仍然恰好 1 个 style），这才是"预算不是变量"的信号——
我停止加预算，改用负 delay 让各条 lane **重叠**而不是排队。

诊断教训：probe 把 `opacity:0`（没开始）和"跑完"都报成 `enterNotVisible`，
标签把我引向了错误方向；真正定位靠的是读 inline style 的实际值。

### 3. 数字无持续动画

`DragTimecode` 只在 progress/drag 变化时重算，parked 场景下读数是死的。
现在补了一个 25fps（40ms）的实时 ticker：手指驱动时让手势接管，parked 且 progress≈1 时
按真实时间累加帧号——一台在跑的摄影机不会停止计时。

## 第八轮（act4 光晕 / 时间码 / 圆环跟手 + act3 去文案）

用户三条 act4 指令与一条 act3 指令，全部实测定因，不靠推断。

### act4-1 时间码「自己涨」+「跳变」——两个独立缺陷，同一处代码

- **自己涨**：上一轮我加的 free run（rAF 累加器，40ms/帧）让计数器在落位后自行前进。
  用户明确否决：「时间不要自己涨，而是拖拽的时候变化」。已整段删除。
- **跳变**：读数原本有**两个真相源**——手指按下时用 `signedDragProgress`，抬起后回落到
  `timeline.progress`。两者不一致，所以松手瞬间从 `baseFrame + signed*dragSpan` 跳到
  `baseFrame - (1-progress)*enterSpan`。现在只有一个源（scene 自身 scrub），
  入场 0→50 帧（= 00:00:02:00），退场镜像 `1-raw` 走回 0。
- 实测：最大单帧跳变 1 帧（物理最小步长），停手后 1 个值不变，上限正好 00:00:02:00。`FAILED=[]`
- 副产物：`signedDragProgress` 变成只写不读的死状态，已从 SceneFlux/父组件/依赖数组清除。

### act4-2 光晕在圈内而非圈外

进度弧画在 200 viewBox 的 r=91（即 shell 的 91%）。原光晕四层全部**窄于**该半径
（wash 渐变 72% 处已透明、core 70%、breath 84%、orbit 91%），光全落在圈内，圆环读作亮盘。
现在四层都从弧半径起向外开：wash 168%（中心 0-52% 透明）、core 91% 仅向外投影、
breath 118%、orbit 106%。中心留空给时间码。

### act4-3 圆环不跟手 / 每次拖重置

**根因**：`ProgressHaloGraphic` 读的是 `useAnimateTimeline().progress`，即 scene 的**入场**
进度——act4 落位后该值恒为 1，所以弧永远停在 `strokeDashoffset: 0`。
实测：47 帧主动拖拽期间只有 1 个值。改读 `dragProgress`（TickBar 用的同一个实时手势值），
而 `handleDragStart` 每次抓取都 `set(0)`，正是用户要的「每次拖都是直接重置」。
光晕 scale 0→2 由同一个值驱动，弧与光不可能失步。
实测：弧随手指 1.000→0.895，停手保持 0.835。`FAILED=[]`

### 探针又一次骗我（本场第五次）

`act4-ring-follow.mjs` 用 `Number(getComputedStyle(arc).strokeDashoffset) || 0`。
计算值是 `"0.5px"` 这类长度字符串时 `Number()` 得 NaN，`|| 0` 把它静默压成 0.000——
所以修复前后报告完全相同，我差点二次返工。改用 `parseFloat` 后立刻显示真实轨迹。
**教训写进规程**：任何读 computed style 数值的探针，禁止用 `Number(x) || 0` 兜底。

### act3 去文案（用户指令的无争议部分）

只留 `s03.name`（调度 / DIRECTING），按字符 stagger 上升 + infinite 呼吸。

0/20 在停手时还有动作。

## Act 5 闭幕式 — 舞台灯光 + 挨个从下往上 (measured)

用户诉求三条：`不要那个「每一帧，听你调度」`（该句在 act3 标题、act5 标题、footerHint、hero
四处重复出现，是我自己的问题）、`缓慢打开灯光入场，背景是个舞台`、`挨个从下往上运动，直到居中`。

1. **文案去重**。`s05.title` 改为「灯光落下，戏散场。」/「The lights come down.」；act3 标题整段
   删除，只留 `s03.name` = 调度。全库 `每一帧` 仅剩 `hero.slogan`（另一个页面，语境成立）。

2. **灯光缓慢打开**。`s05-spotlight` enter 760ms → 6200ms，起点 `delay -2600`。760ms 在落屏前

   在屏幕上根本不存在。

3. **挨个从下往上**。credit 位移 `y: 28 → 140`，enter 360ms → 1500ms。28px 在该字号下是"淡入
   带一点漂移"，不是"运动"。

4. **绝对偏移，不再链式**。credits 与 `s05-the-end` 全部以 `lastTitleWordId` 为唯一 leader，

   预算而非单项时长——标题那轮实测首个间隔 299ms（authored 950ms），后续间隔却精确。绝对偏移
   没有可漂移的依赖。同一处删掉因此失效的 `lastCreditId`。

## act5 落地后 ~9s 空台（真机实测修复）

**症状**：五幕连跑（reel-smoke）报 `tp-scene--05: deadPlate` —— 511 帧在屏内、19 条
lane、0 条在动。而单独的 act5 探针此前实测 credits 依次 settle、THE END 有 85 个不同位
置。两者都没错：诊断显示落地后**前 541 帧（约 9s）** credits 冻在
`opacity:0; translateY(140px)`，动画在那之后才开始。reel 每幕只等 9000ms，所以只看到空台。

**根因（我自己引入的）**：延迟是**叠加**的。credits `waitFor` title → title `waitFor`
kicker → kicker `waitFor` 6200ms 的 spotlight 亮灯，再加上 `titleStartMs 2450` 与
`CREDIT_START_MS 4200`。四段串起来 ≈ 9s，观众先看 9 秒空舞台。

**修法**：全部改为锚定 `s05-slate`（clock 0 起、320ms 的早 lane）+ 绝对偏移，
titleStart 5200 / creditStart 7200。亮灯与文字因此可以**重叠**而不是排队。

**实测**：credits settle 从 frame 724..825 前移到 282..383（仍严格顺序、间隔 25 帧、
各走满 140px）；首次移动距落地 credit0 3.21s / credit4 4.88s / THE END 6.51s，全部落在
可见窗口内。reel-smoke act5 由 0 条在动变为 8 条，`FAILED=[]`。

**本轮三个假警报（都是探针错，不是代码错）**：
1. `neverLanded` —— 同一探针重跑得到 970 landed 帧，是 flake。
2. `s05-title-word-0: visible:false` —— 量的是 animate host，它 `display: contents`，
   按设计不生成盒子。实测 18 个字符全部绘制、box 343x93、词间距 12px、正常折 2 行。
3. `titleText: "Thelightscomedown."` —— 读的是 `textContent`；空格由 flex
   `column-gap: 0.24em` 承担，本来就不在文本里。
4. kicker / title「never move」—— 它们是领跑 lane，在落地前跑完是正确行为。
